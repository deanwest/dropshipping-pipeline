**1\. Global Shopify Rules**

**Theme access**

•	Theme files ARE editable through this connection. Read with graphql\_query (theme { files }), write with graphql\_mutation \+ themeFilesUpsert. This includes creating new sections/\*.liquid files, editing existing sections, config/settings\_data.json, all templates/\*.json and sections/\*-group.json.

•	Only the live theme and demo themes are restricted. Never claim theme access is unavailable without an actual tool error.

•	All writes go to the DRAFT theme, never the live or published theme. Confirm the draft theme ID in Phase 0 and reuse it from build\_state.json.

•	themeFilesUpsert validates section schema on write; a successful write with no userErrors means the section is valid.

**Known destination API constraints**

These are expected behaviors, not failures. Handle them without stopping and without silently degrading the build.

•	Font handles are validated server-side on write. An invalid handle rejects the entire config/settings\_data.json upsert. Never respond by falling back to the theme's default font. Resolve against the real Shopify font list and re-write. Shopify may serve a free equivalent in place of a licensed family (for example a Monotype family rendering as its open-source alternative). That substitution is expected and is not a failure, but the actually served family must be confirmed in the browser and recorded in build\_state.json.

•	custom\_css entries must be complete CSS rules with a selector. Bare declarations are rejected with a generic "Invalid CSS value" that names no entry. Write every entry as selector plus block. Each entry is auto-scoped to \#shopify-section-\<id\>, so a custom\_css rule cannot target the section root itself; to add space around a full-bleed section, apply margin to its outermost inner wrapper instead.

•	A schema setting may not declare an empty string default. Omit the default key entirely rather than setting "".

•	Overwriting config/settings\_data.json replaces global colour schemes, card styles, badge settings and typography for every template in that theme, not only the page being built. Read the existing file first and preserve any setting the model gives no signal for, rather than writing a fresh file from defaults.

•	Shopify Admin GraphQL is cost-throttled. Batch aggressively, and treat throttling as the retryable tool error in Section 10\.

**Cleanup rules (apply in every phase, whenever encountered)**

•	Remove all email capture: newsletter sections, signup blocks, email pop-ups.

•	Remove all pop-ups.

•	Clear theme-vendor demo branding: brand\_headline, brand\_description, vendor copyright lines, vendor announcement blocks.

•	Footer group: only the footer section stays. Delete dividers, tickers, email blocks, and any announcement bar from the footer group. (The header announcement bar is different: if the model has one, replicate it exactly.)

**Styling precedence**

1\.	When a model exists, copy the model exactly: buttons, backgrounds, footer colors, fonts, spacing.

2\.	Only when a value truly cannot be read from the model HTML: buttons black background / white text / no hover animation, section backgrounds pure white, footer pure black with pure white text. This fallback applies per value, never to a whole region. If the model footer is readable, copy it; never apply the black-footer fallback because footer CSS extraction came back thin.

**Critical Visual Fidelity**

•	Fonts and visible section background colors are critical. Prioritize them over minor spacing differences or missing decorative content.

•	**Typography mapping:** Read every font\_picker setting in config/settings\_schema.json and trace where each setting is actually used in the theme's Liquid/CSS before assigning fonts. Never assume setting names. Recover the model's actual Shopify font handle from its CSS/font files and map it to the corresponding theme setting.

•	**Background mapping:** Match the model's actual visible background color, not only its color-scheme name or ID. Never assume the same color-scheme ID has the same colors on both stores. Prefer an existing draft-theme color scheme whose actual colors match the model. Never modify a shared color scheme unless every section using that scheme will still match the model. If needed and supported by the theme, create or use a dedicated matching scheme instead.

•	**Critical verification:** Before Phase 1 can close, strictly compare the model vs draft for the **header, the first two content sections, and the footer**. Verify font-family, font-size, font-weight, letter-spacing, text color, and effective visible background color. Any visible font-family or background mismatch in these regions is a DIFF that must be fixed before completion.

•	For all remaining sections, include first-heading font-family and effective visible background color in the existing measured verification pass. Do not repeatedly chase minor typography differences outside the header, first two sections and footer unless they are clearly visible.

•	Font family is inherited from global theme settings and is therefore usually correct everywhere once set. The values that actually drift per region are size, weight, letter-spacing, text-transform and colour. Verify those explicitly rather than assuming a correct family means correct typography.

•	When checking backgrounds, inspect both the .shopify-section root and the visible full-width child wrapper supplying the background. A transparent section root does not prove that the backgrounds match.

•	Never silently substitute a different font or intentionally change unrelated section colors. If an exact font or background cannot be reproduced through the theme's supported settings after verification, record the exact limitation in open\_issues rather than entering an endless retry loop.

**Copy lock for Phases 1–3**

•	Until Phase 4 begins, never rewrite, paraphrase, improve, shorten, expand, generate, or otherwise alter any customer-facing copy from the inspiration store.

•	Copy all customer-facing text exactly as captured.

•	The only permitted text changes before Phase 4 are exact plain-string replacements of the inspiration store's brand name or domain when required, plus removals explicitly required by the Cleanup Rules.

•	Never change surrounding wording when replacing a brand name or domain.

•	If unsure whether text should change, leave it unchanged.

•	Original store copy is generated only in Phase 4\.

**Structural fidelity and custom-theme code**

•	A matching Shopify base theme does NOT mean the model store is stock. Many stores use Dawn or another base theme with heavily modified Liquid, CSS, custom sections, custom headers, custom navigation, and source-only behavior. Those customizations are part of the design and must be reproduced when they are visible.

•	Never force a model section into the draft theme's stock section just because the base section type exists. Use the stock section only when the destination schema and rendered stock markup can reproduce the model's visible structure and behavior.

•	If the model has source-only wrappers, modifier classes, custom CSS assets, custom elements, desktop/mobile slider behavior, extra navigation rows, custom header/footer structure, or any other visible structure that the draft stock section cannot generate, promote that section to a CUSTOM REPLICA instead of approximating it.

•	CUSTOM REPLICA means rebuilding the model section from the captured rendered DOM and captured CSS inside a new sections/ai-\<key\>.liquid file, with settings for images/text/links and only the minimal local JavaScript needed for visible interaction that the destination theme does not already provide.

•	Header and footer are not exempt. If their model structure cannot be generated by the destination stock header/footer, build ai-header-replica.liquid and/or ai-footer-replica.liquid and place those types in the appropriate section group JSON.

•	Theme-owned customization is supported. Third-party app output remains excluded under the app rules. Do not confuse custom theme code with an app.

•	Structural fidelity takes priority over staying stock. A correct custom replica is better than an incorrect stock section.

**Structural versus cosmetic (custom replica calibration)**

•	Structural means: band or row count, grid versus carousel, column count, item flow and wrap state, wrapper hierarchy, custom-element behavior, and any difference between the desktop and mobile composition. A structural difference the destination cannot generate forces CUSTOM REPLICA.

•	Cosmetic means: padding, margin, font-size, font-weight, letter-spacing, text-transform, colour. A cosmetic difference does NOT force a custom replica and may be carried as section-scoped custom\_css on a STOCK-SAFE section.

•	Escalation: if the cosmetic set for one section grows past roughly six declarations, or any of it begins changing layout mode rather than appearance, treat that section as structural and promote it.

•	This calibration exists so the custom-replica path stays targeted. Rebuilding every section by hand is slower, discards the destination theme's own responsive CSS, and creates more surface to get wrong.

**Theme image settings**

•	image\_picker rejects https URLs and accepts only shopify://shop\_images/\<stored-filename\>.

•	Workflow: fileCreate (originalSource \= any public URL) → query the file back and read image { url } → take the actual stored filename (Shopify may rename or append \_1) → set "image": "shopify://shop\_images/\<stored-filename\>.png" with no domain, query string, or version → write with themeFilesUpsert.

•	Batch: one fileCreate for all images of a step, one themeFilesUpsert for all files of a step.

**Product safety (absolute)**

•	Never hardcode the model store's products, prices, variants, product images, or fabricated product cards into any section, stock or custom, to make it appear populated. Product and collection sections stay bound to real Shopify product/collection data. If the referenced products do not exist in the user's store, an empty product area is CORRECT; leave it empty.

•	A section whose only difference from the model stems from absent product or collection data in the user's store is NOT a DIFF. Record it once as expected and exclude it from the fix loop permanently.

**Collections**

•	Sections that reference collections render placeholder clipart until real collections exist. Create placeholders with collectionCreate using the model’s exact collection titles, set image: { src: \<model image URL\> } in the create call, then publish to the Online Store publication (publishablePublish, publication ID from the publications query where app title \= "Online Store"). If the collection image is not in the saved HTML, use the collection page og:image.

**Never call Higgsfield's show\_plans\_and\_credits tool or open any Upgrade Plan, billing, or subscription widget.**

**2\. Replication Procedure**

Applies to Phase 1 (home page) and to Phase 2 when the user wants the exact model product page design. Goal: a pixel-level copy of the model page on the user’s draft theme, not an approximation.

**2.1 Source of truth**

The uploaded .mhtml capture is the only build source for page markup, layout, section structure, and CSS. The model URL may be used only to record the model domain, fetch og:image for collection pages, or recover an exact missing asset URL that the MHTML references but failed to preserve. Never use fetched page HTML as a substitute build source, never use a text-converted web fetch to infer layout, and never use Apify or any scraping actor. If no capture has been uploaded, ask for it and stop.

Capture instruction to give the user (two lines): "Open the model page in Chrome on desktop, maximise the window, and scroll slowly all the way to the bottom so every section loads. Then press Ctrl+S (Cmd+S on Mac), choose ‘Webpage, Single File’ in the format dropdown, and upload the .mhtml file it saves."

The only accepted format is Chrome's Webpage, Single File (.mhtml). Judge by contents, not extension. An MHTML file is a MIME multipart document: the HTML is quoted-printable, the CSS is split across separate text/css parts, and every image is its own part whose Content-Location header preserves the original CDN URL. That one file therefore carries everything the build needs: the CSS and the original image URLs. Do NOT use the SingleFile extension. If a SingleFile extension save, an HTML Only save, or a Webpage Complete save is uploaded instead, do not build and do not work around it; ask for the .mhtml re-save with the instruction above.

**2.2 Step A: Preflight the file**

Parse the file offline with Python using the MHTML-aware skeleton in Appendix A (never paste the raw capture into the conversation, and never parse MHTML with ad hoc regex; the quoted-printable encoding corrupts naive extraction). Keep the detailed preflight internal. Only tell the user if there is a problem that requires their action. 

Record it in build\_state.json:

Shopify check: if the capture contains no shopify-section elements, the model is not a Shopify Liquid store. Stop, do not show any technical findings, and say exactly: "This store can’t be used as inspiration because it isn’t built with Shopify. Send me a different store to take inspiration from. You can find stores that use your same theme at https://ThemeSpotter.com, or find a new store, detect its theme and download it onto yours." Then wait.

1\.	Base theme match: read Shopify.theme \= {...} (name, theme\_store\_id, schema\_name, schema\_version when present) if the capture kept any scripts, and compare with the draft theme’s config/settings\_schema.json theme\_info. State SAME THEME, SAME THEME DIFFERENT VERSION, or DIFFERENT THEME. Chrome MHTML normally strips scripts, so the normal fallback is to compare the model’s CSS-variable vocabulary, core asset names, stock section markup, and custom-element vocabulary against the draft theme. Report fallback matches as INFERRED. The internal theme determination never substitutes for the mandatory ThemeSpotter confirmation required from the user in Phase 1\. If the internal determination is DIFFERENT THEME and the user has already confirmed SAME THEME, see the conflict rule in Phase 1\.

2\.	Sections found: count .shopify-section elements in order. Save each section’s full rendered HTML fragment separately under capture\_sections/\<order\>\_\<key\>.html; do not rely only on a summarized manifest when rebuilding custom structure.

3\.	CSS asset map: build a map of every text/css MIME part by both Content-Location and Content-ID. For every section, record every \<link rel="stylesheet"\> inside that section and resolve it to its exact captured CSS part. Also record every \<style\> block inside the section. Then do a CSS dependency sweep across ALL captured CSS parts for rules that target the section’s exact ID/source key or uncommon classes/custom elements present in that section. This catches model-owner CSS stored globally in files such as base.css, theme.css, custom.css, or a custom header stylesheet rather than linked directly inside the section. The sweep is mandatory and is implemented in Appendix A; a section’s CSS is not considered captured until the sweep has run for it. Save the relevant combined section CSS under capture\_sections/\<order\>\_\<key\>.css, preserving media queries and keyframes. Do not copy an entire global stylesheet when only a few rules are needed, and do not assume a same-theme destination has equivalent CSS merely because an asset filename is familiar; compare the actual captured rules when the model behavior differs.

3b. Image sources: count image MIME parts and how many have an http(s) CDN URL in Content-Location. Those URLs go straight to fileCreate as originalSource. Fallbacks only for an image without a URL: (a) if alt is a filename, confirm that file in the store’s Files library and use it; (b) decode the image bytes and upload through stagedUploadsCreate → fileCreate; (c) use the model URL only to harvest the missing image CDN URL, never as a build source for markup or CSS. If @font-face rules exist but no usable Shopify font handles are extracted, resolve font mapping before building rather than silently falling back.

4\.	Lazy or incomplete capture: flag any section with no meaningful rendered content where the page clearly expects content, unloaded placeholders, or skeletons that are the only visible state. Hidden skeleton markup by itself is not a failure when the actual loaded content is also present. If the capture is genuinely incomplete, ask the user to re-save after scrolling to the bottom and stop.

4b. Capture viewport check (mandatory). A capture saved from a narrow browser window is a MOBILE capture: different column counts, mobile-only rows present, desktop-only rows absent, sliders in a different state. Every downstream decision made from it will be internally consistent and completely wrong. Infer the width the capture was saved at before building. Signals: rendered img width/height attributes against the model’s \--page-width; presence of desktop-only wrappers and grid--N-col-desktop classes; presence of sections that are display:none at desktop; slider activation state; number of visible items per row. If the capture resolves to below roughly 1000px, do NOT build. Tell the user in plain words to maximise the browser window, reload the page, scroll to the bottom, and save again. Record the inferred capture width in build\_state.json.

5\.	App vs theme customization: detect PageFly, GemPages, Shogun, Replo, EComposer, aigenblock, shopify-app-block, known app hosts, and injected review/upsell widgets. Those follow the app rules. Separately detect theme customization: source-only stylesheet assets, custom section names, extra wrappers, custom elements, extra header/navigation bands, model-only modifier classes, altered slider behavior, custom grid/list behavior, and source-only CSS. Theme customization is supported and must NOT be discarded as an app.

5b. Personalization and experiment variants. Some model pages ship several variants of the same region with only one visible (geo-targeted banners, A/B test branches, personalization modules). Build only the branch that is actually rendered visible in the capture, drop the hidden branches, and note in open\_issues that the page may render differently for other visitors.

6\.	Behavior inventory: per section record visible behavior at desktop and mobile when detectable from markup/CSS: grid vs flex, columns, row count, slider/carousel, horizontal overflow, sticky behavior, accordion/details, tabs, autoplay, hover-only content, desktop/mobile visibility, and any custom element responsible for it. If the destination theme already defines the same custom element (for example Dawn’s slider-component, sticky-header, header-drawer, details-modal), reuse that behavior. If it does not, the custom replica may use minimal section-scoped vanilla JavaScript to reproduce the visible interaction.

7\.	Native media vs third-party embeds: a normal \<video\> or \<picture\> hosted on the model store’s Shopify CDN is theme content, not an app. Preserve its container, aspect ratio, poster, and controls/behavior when practical. If the destination stock section cannot host the media type, that is a CUSTOM REPLICA trigger, not an open\_issues entry. Third-party players/embeds remain open\_issues.

If the file fails the Shopify check, section completeness check, or capture viewport check, stop and get a better source. Heavy customization is NOT a reason to stop.

**2.3 Step B: Extract into manifest.json plus section fragments**

Produce a manifest with Appendix A and adapt as needed. The manifest is an index; the saved HTML/CSS fragments are the authoritative custom-replica source. Per section, in page order record:

•	order, section\_id, source\_key, dom\_id, root classes

•	base\_section\_type: the closest stock type only when confidently inferred from semantic classes/data attributes or a draft-theme section filename. Never infer a type from a generic class such as section-template--....

•	linked\_stylesheets: exact model stylesheet locations used inside the section, plus whether the same asset/rules exist in the draft theme

•	class\_tokens: uncommon/structural class names used to find owner CSS in global captured stylesheets

•	inline\_style, global\_matching\_css, and section\_css\_file

•	html\_file: saved full rendered section fragment

•	custom\_elements: custom HTML elements found inside the section (slider-component, secondary-nav, etc.)

•	headings, body\_text, buttons, links

•	images: each image resolved through the image map with alt, original CDN URL, rendered dimensions/aspect when available

•	svgs: every inline SVG verbatim

•	layout\_hints: visible width behavior, max width, grid/flex, column count, row count, gaps, alignment, image position, background, overflow, slider classes, control visibility

•	behavior\_hints: slider/carousel, sticky, details/accordion, tabs, video, hover state, custom-element dependency

•	app\_content: true only for actual app/page-builder output

•	stock\_candidate: whether a plausible stock section type exists in the draft theme; this is only a candidate, not permission to use STOCK

Page globals:

•	Fonts: extract @font-face, CSS vars \--font-heading-family, \--font-heading-weight, \--font-body-family, and Shopify CDN handles exactly as captured. Never guess a handle. When a Shopify CDN font URL contains a font handle in the filename, such as work\_sans\_n6.\<hash\>.woff2, use work\_sans\_n6 exactly as written. Never guess, add, remove, or rearrange underscores in a handle recovered directly from a Shopify CDN URL. Also record each @font-face rule’s font-family, font-weight, and font-style so the extracted handle can be matched to the rendered typeface. If no usable Shopify handle exists in the captured URL, use the @font-face metadata and the draft theme’s font settings to identify the correct supported font. Never silently invent or guess a font handle.

•	\--page-width, heading scale, letter spacing, line height, color variables, button variables.

•	Heading scale table: record the model’s computed font-size for each heading class it uses (h0, h1, h2, h3, h4, h5 or the theme’s equivalents) and for .rte headings. A forked theme frequently rescales these, so a destination class of the same name is not the same size. Build the destination’s equivalent table from the draft theme and map by rendered pixel size, not by class name.

•	Announcement bar: full visible structure, messages, slider behavior, arrows, socials, autoplay, colors, font weight, linked stylesheets.

•	Header: save the full rendered header section fragment and all CSS linked inside it, plus any global CSS rules targeting its classes. Record number of horizontal bands/rows, search field vs icon, logo position and dimensions, nav rows, secondary nav, dropdown/mega-menu structure, icons, sticky behavior, custom elements, desktop/mobile visibility, and any model-only stylesheet assets. Record typography per role: nav link family, size, weight, letter-spacing, transform and colour; announcement message size, weight and colour.

•	Footer: save the full rendered footer fragment, every stylesheet linked inside it, and any global CSS rules targeting its classes. Record: number of rows or bands, block and column count with each block’s rendered width, layout mode (grid or flex, wrap state), effective visible background per band, logo and payment icon rendered sizes, social row, navigation columns, policy row, copyright line, custom elements, desktop and mobile visibility. Record typography per role: block heading family, size, weight, letter-spacing, transform and colour; link family, size, weight, letter-spacing and colour; caption and copyright size and colour. Families are inherited globally, so the values that must be verified here are size, weight, letter-spacing, transform and colour.

Header and footer are content, not configuration. Everything inside them is a build target, exactly like a section. Any header or footer region with no equivalent in the destination’s stock header/footer becomes a CUSTOM section with "enabled\_on": { "groups": \["header"\] } or \["footer"\], placed in that group’s JSON in the model’s DOM order. Regions a settings checklist reliably misses: secondary or category nav bars, promo strips, utility rows, store locator links, app badges, payment icon rows, expanded search fields, and any second or third band.

Show the user only a compact table: order, inferred type, STOCK/CUSTOM candidate, images count, headline. Never dump the manifest or technical compatibility analysis.

**2.4 Step C: Classify every section by reproducibility, not by name**

For every manifest entry decide in this order:

1\.	SKIP: newsletter/email capture, pop-ups, app review widgets, third-party app blocks, and vendor demo blocks required by Cleanup Rules. Log the reason.

2\.	VERBATIM COPY: self-declared Custom Liquid/custom-code blocks follow the existing verbatim rule: copy captured HTML/CSS into the appropriate custom-code location, re-upload images, localize internal links, and drop captured scripts because the rendered DOM is already their output. App code is excluded.

3\.	STOCK-SAFE: use the destination stock section only if ALL of the following are true: • base\_section\_type exists in the draft theme. • Every visible model content element has a valid home in the destination schema. • Every visible structural difference can be generated by the destination Liquid/schema. Cosmetic differences may be carried as section-scoped custom\_css under the Structural versus cosmetic calibration in Section 1\. • The destination stock markup can reproduce the model’s desktop/mobile flow: grid/flex mode, columns, row behavior, slider/carousel state, item widths, alignment, image placement, controls, and major wrappers. • No source-only wrapper or custom element is required to make the visible layout work. Configure STOCK-SAFE through Setting Inversion in Appendix B.

4\.	CUSTOM REPLICA: use this whenever any STOCK-SAFE requirement fails, even if the model and draft use the same base theme and the base section type exists. This includes a Dawn multicolumn that the model customizes into a desktop carousel, a custom grid navigator, personalized banner, custom header/nav, heavily modified image banner, or stock section with source-only markup that changes visible structure.

**open\_issues gate (applies everywhere in this document)**

Before writing anything into open\_issues, state in the entry itself that you considered building it as a CUSTOM REPLICA and why that failed. "The destination theme has no setting for this" is never a sufficient reason, because a custom replica does not need a setting. That sentence is the single most common way a buildable element gets written off, and it is not accepted. Only these reasons qualify:

•	the content is rendered at runtime by a third-party app and is therefore not in the capture;

•	the asset is a licensed font, or a media format the destination cannot host;

•	the content is real product or collection data the user’s store does not have yet;

•	reproducing it would require editing a shared global stylesheet in a way that breaks other templates.

Anything else that exists in the capture gets built. open\_issues is for genuine impossibility, never for difficulty, and never for "the stock section almost does it."

**CUSTOM REPLICA build rules**

•	Create sections/ai-\<key\>.liquid from the saved rendered HTML fragment and exact captured section CSS, not from a guessed equivalent section.

•	Preserve the model’s visible DOM hierarchy, structural wrappers, class names, relevant data attributes, inline SVGs, media queries, keyframes, and modifier classes. Remove analytics-only wrappers/attributes when they have no visual/behavior role. Remove actual app markup.

•	Scope copied CSS to \#shopify-section-{{ section.id }} wherever possible so it cannot leak into other sections. Preserve selectors needed by reused destination custom elements. Replace hardcoded model section IDs in CSS/HTML with section-scoped IDs based on {{ section.id }}.

•	Create schema settings for every visible image, heading, text/richtext, button label, link, collection reference, and other content that later phases must replace. Keep structure fixed; settings change content, not the replicated layout.

**2.6.0 Measurement validity (run before any measurement, every time)**

No measurement pass is usable until all four of these pass. A pass that skipped them is discarded, not reported.

•	Preview isolation. Shopify stores the last preview\_theme\_id in a cookie. Load the draft as ?preview\_theme\_id=\<draft id\> and load the model with its own explicit theme parameter or in a separate browser context. After loading, confirm the two pages are genuinely different documents by comparing a value that must differ, such as shop domain or section id prefix. Two identical measurement sets across model and draft is a red flag, not a pass. Never report zero diffs without that confirmation.

•	Viewport assertion. After resizing, read window.innerWidth on each tab and confirm it. A resize call reporting success is not proof; windows frequently refuse to resize. If 1440 cannot be reached, both tabs must still be measured at the identical width, that width recorded in build\_state.json, and every comparison treated as relative rather than absolute. Never compare measurements taken at two different widths.

•	Reveal-safe scrolling. Themes with scroll-triggered reveal animations keep sections at opacity 0 until an intersection observer fires. Do not jump to a scroll offset. Scroll from 0 to full height in increments no larger than 400px with a short pause at each step, then settle, then measure. Before measuring, assert that no measured section still carries an offscreen or unrevealed state class and that no measured section has computed opacity 0 or visibility hidden. A blank screenshot or a zero-height section is a measurement failure, never a finding about the build.

•	Font readiness. Await document.fonts.ready before reading any typography value.

3\.	Structural verification at 1440px: open model and draft at the same asserted viewport, scroll both per the reveal-safe rule, and measure per section: • section top, height, visible width/max-width and major container width • direct visible child count • computed display, grid-template-columns, flex-direction, flex-wrap, gap, overflow-x • number of visible rows and approximate columns by grouping the first repeated items’ bounding boxes by Y position • first 8 repeated item bounding boxes (x,y,width,height) • slider/carousel classes/state, visible slide count, slide width, controls/counter visibility • major image rendered boxes and aspect ratios • heading/body/button alignment. A 4-item single-row desktop carousel is structurally different from a 4+3 wrapped grid even if it uses the same images. Treat that as a hard DIFF.

3b. Gap attribution (mandatory). Height, top offset and band count are measured, not narrated. Where model and draft differ by more than 8px on any section, header band or footer region, name the specific element in the model that occupies that difference, confirmed by reading the model DOM at that position. Write the attribution down before deciding what to do with it. An explanation that defers work ("the logo arrives in a later phase", "the store has no products yet", "theme version drift") may not be asserted without opening the model at that position first. If the attributed cause is missing content, build it. Only a gap whose attributed and verified cause is a genuine limitation may be recorded under the open\_issues gate, and that entry must state the cause, not the symptom.

4\. Missing a model header row or collapsing a custom search/header into the stock destination header is a hard DIFF.

A model footer that renders five blocks in one row against a draft that wraps to three plus two is a hard DIFF, not a spacing difference. Then compare block heading and footer link font-size, font-weight, letter-spacing, text-transform and colour, plus copyright and caption size and colour. Fix through a real setting, the model owner’s captured Custom CSS, or promotion to ai-footer-replica.liquid. Never set footer type sizes by eye.

5\. 6\.	Auto-fix loop: fix every structural DIFF before chasing minor styling. If the section is stock and the required structure has no valid schema setting, PROMOTE TO CUSTOM REPLICA immediately. Rebuild, remeasure, and continue. Do not record a reproducible structural mismatch as theme-version drift.

7\.	Responsive sanity pass: for every CUSTOM REPLICA, the header and the footer, check at approximately 390px wide. Preserve the source CSS media queries and confirm there is no horizontal page overflow, overlapping text, or broken stacked layout. Exact mobile pixel matching is secondary to desktop unless the source clearly provides a different mobile composition.

8\.	Screenshot comparison: when browser screenshot capability is available, inspect model and draft top/middle/bottom yourself after the measured pass and fix obvious visual differences before asking the user. If direct screenshot comparison is unavailable, ask the user for exactly 3 screenshots at 1440px wide of the DRAFT preview: top, middle, bottom, side by side with the model regions. •	Keep a jobs.txt map of job ID → target slot whenever more than one job is in flight. Poll to completion before importing.

**Import**

•	Results are public CloudFront URLs. Import with fileCreate using the CloudFront URL as originalSource. Never use staged uploads for these. Batch imports. Query stored filenames after upload and read settings back before reporting success.

**10\. Failures and Recovery (single source of truth)**

| Situation | Action | Counts toward stop rule? |
| :---- | :---- | :---- |
| Higgsfield "too many jobs" / rate limit | Wait 15 s, retry same job unchanged | No |
| Generic image generation failure | Wait 20 s, retry once same reference; if it fails again and a second suitable reference exists, retry once with it; only then mark the target failed and log to failed\_images.txt | Yes, one failure per target after full escalation |
| Credits exhausted / hard limit | Stop new submissions, keep every rendered image, finish all non-image work, flag remaining slots as incomplete for a later re-run | Stops image work only |
| Any Shopify or Higgsfield tool error | Wait 30 s, retry; wait 30 s, retry again; report only after the third failure with the actual error text | n/a |
| Shopify GraphQL throttling | Back off and retry the same batched call; reduce batch size only if it throttles twice | No |
| themeFilesUpsert userErrors | Check Known destination API constraints in Section 1 first, fix the payload and rewrite; never leave a section file invalid | n/a |
| Invalid font handle on settings write | Do NOT fall back to the theme default. Resolve against the real Shopify font list and rewrite, then confirm the served family in the browser | n/a |
| Browser resize refuses / wrong viewport | Discard the measurement pass. Re-assert innerWidth, or measure both pages at the same alternate width and record it | n/a |
| Measured section blank or zero height | Treat as a measurement failure, re-run with reveal-safe scrolling. Never record it as a build finding | n/a |
| Nearing context limit | Write build\_state.json and checkpoint.json (last completed step, section, or slot), tell the user the exact resume instruction | n/a |

Stop rule: stop the run only after 3 distinct targets fail in a row after full escalation, or on a hard account/credit limit. Raw retries on one target never count as separate failures. Never stop a batch for a single item, never ask for confirmation on individual failures, never claim tools stopped or access was cut without an actual tool error.

Adapt freely; the output shape and safety rules matter more than this exact code. `def infer_capture_width():`

`# ---- generic-class guard --------------------------------------------------`  
`GENERIC_PREFIXES = ("section-template--", "section-sections--", "shopify-section", "color-scheme-")`

`def source_key(el):`

`def base_type(el):`

`def linked_css(el):`

            `continue`  
        `links.append(href)`  
        `if href in css_by_ref:`  
            `chunks.append(css_by_ref[href])`

    `for node in el.find_all(True):`  
        `for c in node.get("class", []):`  
            `toks.add(c)`  
        `if node.name and "-" in node.name:`

            `if len(t) > 5 and not t.startswith(("color-scheme-", "shopify-", "section-template--",`

`def global_css_sweep(el):`

    `key = source_key(el)`  
    `toks = class_tokens(el)`  
    `hits = []`  
    `for rec in css_records:`  
        `for m in RULE_RE.finditer(rec["text"]):`  
            `rule = m.group(0)`  
            `sel = rule.split("{", 1)[0]`  
            `if sid and sid in rule:`  
                `hits.append(rule); continue`  
            `if key and key in rule:`  
                `hits.append(rule); continue`  
            `probe = rule if rule.lstrip().startswith("@media") else sel`

                    `hits.append(rule); break`

    `for h in hits:`  
        `k = h.strip()`  
        `if k not in seen:`  
            `seen.add(k); out.append(k)`  
    `return "\n\n".join(out)`

**Appendix B: Setting Inversion and STOCK-SAFE test**

Never rely on a memorized class-to-setting table. Derive the destination mapping from the destination theme itself, once per section type.

1\.	Read sections/\<type\>.liquid. Extract the {% schema %} and record every section/block setting: id, type, default, option values, range constraints.

2\.	Find where each setting is used in Liquid and how it renders: class, CSS variable, data attribute, text node, image, block loop, visibility or wrapper.

3\.	Invert the model markup into destination settings only when the destination can actually generate that structure. Validate values against schema.

4\.	Reconciliation pass: every model heading, body string, button and image must be consumed exactly once. Then reconcile STRUCTURE, not only content: • model modifier classes that change layout/behavior • wrappers/containers that create extra rows or bands • grid/flex classes and column count • slider/carousel classes and desktop/mobile activation • custom elements and required data attributes • source-only linked or swept stylesheet rules that materially affect layout • header/search/navigation bands and footer bands. If a visible structural requirement has no real destination setting or destination Liquid path, the section FAILS STOCK-SAFE and must be promoted to CUSTOM REPLICA. Do not put that failure in open\_issues.

5\.	Sizes/spacing from section inline styles and owner-entered Custom CSS may be carried into a STOCK-SAFE destination as section-scoped custom\_css under the Structural versus cosmetic calibration. Later CSS rules override earlier ones.

6\.	Global font/color/page-width/button values are inverted from destination global settings and model computed/source values. Map headings by rendered pixel size using the heading scale table, never by class name.

7\.	A section is STOCK-SAFE only after both content reconciliation and structural reconciliation pass. "Same base theme" alone is never enough.

**Appendix C: CUSTOM REPLICA conversion checklist**

Use this for every section promoted from stock or originally custom.

1\.	Start from the saved capture\_sections/\<...\>.html fragment and its saved section CSS including the global sweep, not a simplified description.

2\.	Remove actual app blocks, tracking/analytics-only nodes, scripts, hidden skeleton-only states, and duplicate inactive personalization variants. Keep the currently rendered visible branch.

3\.	Preserve the visible hierarchy/classes. Replace model-specific section IDs with {{ section.id }}-based IDs. Scope copied CSS to the new section root without breaking media queries, pseudo-elements or reused destination custom-element selectors.

4\.	Convert content into schema settings: images, headings, rich text, buttons, links, collection references. Preserve exact model copy through Phase 3\. No schema setting may declare an empty string default.

5\.	Import images/backgrounds and rewrite sources. Preserve inline SVGs exactly.

6\.	Localize internal links and Shopify functions. Search/cart/account/home must point to the user’s store.

7\.	Reuse destination theme behavior when the same web component exists. Otherwise implement only the minimal local JS necessary for the visible behavior. No tracking, personalization, analytics, or app JS.

8\.	For slider/grid sections, explicitly reproduce desktop AND mobile rules for visible item count, item width, row wrapping, overflow and controls. Do not assume the base theme’s default slider breakpoint matches the model’s customization.

9\.	For custom headers, preserve each visible band as its own row/container. Do not collapse search, logo, primary nav and secondary nav into one stock row if the model has separate rows. Use dynamic Shopify routes/cart count where possible.

10\.	Validate section schema, write, preview, and run structural verification under 2.6.0 measurement validity. If custom output still differs structurally, fix the captured CSS/markup mapping before moving to typography.

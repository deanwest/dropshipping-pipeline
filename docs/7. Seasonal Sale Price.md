## **Seasonal Sale Price**

### **The Brief**

* **Q1** — Do you want to start the sale or end it? (Start sale / End sale)  
* **Q2** — Tag(s) to target (one or more, e.g. summer or winter, evergreen)  
* **Q3** — Discount percentage (only needed when starting a sale, e.g. 20\)  
* **Q4** — Should we confirm steps with you? (Yes this is a manual task / No this is a scheduled task)

### **Purpose**

Run a tag-scoped sale on Shopify products by setting a compareAtPrice on every variant of every matched product, so the storefront shows a strikethrough discount. Also reverses the sale. Execute efficiently with minimal context bloat.

### **How the sale works**

This is a compare-at (strikethrough) sale. The variant's actual selling price is never changed. The sale is created by writing a higher compareAtPrice, which the storefront renders as a crossed-out "original" price next to the real price.

compareAtPrice is a display-only anchor. price is the truth and stays put.

For a discount of pct%: compareAtPrice \= price ÷ (1 − pct/100). Example: 20% → price ÷ 0.8; a $80 variant gets a $100 compare-at, still sells for $80, and shows as "20% off".

The computed compareAtPrice is taken exactly to the cent (2 decimal places) — no $.99-style rounding is applied.

Because price is never touched, this is safe to re-run. If a variant already has a compareAtPrice, it is simply recomputed and overwritten — there is no original price to lose.

Ending the sale just clears compareAtPrice back to null. price is untouched.

#### **Phase 1: Fetch and Prepare (Silent)**

Build the tag filter from Q2: a single tag → tag:summer; multiple tags → join with OR, e.g. tag:summer OR tag:evergreen. Products matching ANY listed tag are in scope.

Fetch all matching products via Shopify:graphql\_query:

graphql

query($query: String\!, $first: Int\!, $after: String) {

  products(query: $query, first: $first, after: $after) {

    edges {

      node {

        id

        title

        tags

        variants(first: 100\) {

          edges { node { id price compareAtPrice title } }

        }

      }

    }

    pageInfo { hasNextPage endCursor }

  }

}

Paginate if \>50 products (use after cursor). Save to /home/claude/work/products.json.

If zero products match the tag filter, stop and tell the user — there is nothing to do, and a likely cause is a mistyped tag.

Compute the per-variant changes offline in a Python script. For every variant of every matched product:

* **Start sale:** compareAtPrice \= price ÷ (1 − Q3/100), taken to 2 decimal places (cents). price is left exactly as-is. Any existing compareAtPrice is overwritten. If the computed compareAtPrice is not strictly greater than price (e.g. Q3 is 0), skip that variant and log it — a sale anchor must be above the selling price.  
* **End sale:** compareAtPrice \= null. price is left exactly as-is. A variant that already has no compareAtPrice is skipped (nothing to end).

Save to /home/claude/work/sale.json:

json

\[

  {

    "product\_id": "gid://shopify/Product/123",

    "variants": \[

      {"id": "gid://shopify/ProductVariant/456", "price": "80.00", "compareAtPrice": "100.00"}

    \]

  }

\]

price is included unchanged so the mutation payload is explicit; only compareAtPrice actually differs from the live value. On End sale, compareAtPrice is null.

Output to user: "Sale preparation complete (N products)"

#### **Phase 2: Push Variant Updates in Batches of 10**

Build all batch payloads offline in one Python pass first, writing each batch to its own JSON file. Then fire the mutations with zero bash round-trips between them — this is the single biggest speed-up; data streaming through chat is what makes runs slow.

Execute batched GraphQL mutations, 10 products per call, via productVariantsBulkUpdate (productId \+ a variants array). Use mutation aliases to batch 10 products per call:

graphql

mutation($pid0: ID\!, $vr0: \[ProductVariantsBulkInput\!\]\!,

         $pid1: ID\!, $vr1: \[ProductVariantsBulkInput\!\]\!, ...) {

  v0: productVariantsBulkUpdate(productId: $pid0, variants: $vr0) { userErrors { field message } }

  v1: productVariantsBulkUpdate(productId: $pid1, variants: $vr1) { userErrors { field message } }

  ...

}

Each ProductVariantsBulkInput entry carries the variant id and compareAtPrice. On Start sale compareAtPrice is the computed anchor; on End sale it is null (this clears it).

Request only userErrors in the response.

Check userErrors for failures, log them, continue.

Output after each batch: "Products X–Y sale done"

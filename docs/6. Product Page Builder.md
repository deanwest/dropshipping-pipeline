# **Product Page Builder**

## **The Brief**

* **Q1:** Which products to fill (List of names / By Tag / By Collection / All)

* **Q2:** How many products to create custom pages for (Test With One \- Recommended / 50 / All / Other)

* **Q3:** What product page design should I use? (Build a basic one from scratch / Use the design the Store Builder already made \- called inspiration-universal / Use my own template, named: {template name})

* **Q4:** Image style for the image-with-text sections (Lifestyle / Pure white / Your design, be descriptive)

* **Q5:** Brand voice (Default / Provide your own example)

* **Q6:** Your store name ()

* **Q7:** Remove a tag from each product when it's completed? (Yes, remove this tag: {tag} / No)

* **Q8:** Set completed products to Active? (Yes / Keep current status)

* **Q9:** Should we confirm steps with you? (Yes this is a manual task / No this is a scheduled task)

## **Purpose**

Build or extend a product page template, then fill it per product: create the "universal-with-metafields" template on the draft theme, create every metafield definition, autobind every field to its metafield, write the 3 checkmark benefits, script the 3 image-with-text headers and descriptions, generate a matching image for each header with Higgsfield, write the top 5 FAQ Q\&A, push all of it live by setting product metafields, then finish each product per Q7 and Q8. The student never creates a template, never creates metafields, and never binds a field by hand. Execute efficiently with minimal context bloat.

## **Fixed Metafield Convention (namespace custom)**

* Benefits (checkmark headings): benefit1, benefit2, benefit3 (single line text)

* Image-with-Text headings: iwt1\_heading, iwt2\_heading, iwt3\_heading (single line text)

* Image-with-Text body copy: iwt1\_body, iwt2\_body, iwt3\_body (multi line text)

* Image-with-Text images: iwt1\_image, iwt2\_image, iwt3\_image (file image)

* FAQ questions (top 5): faq1\_q, faq2\_q, faq3\_q, faq4\_q, faq5\_q (single line text)

* FAQ answers (top 5): faq1\_a, faq2\_a, faq3\_a, faq4\_a, faq5\_a (multi line text)

Use plain single line or multi line text metafields for ALL copy, including bodies and FAQ answers. Never use rich text metafields. Plain text cannot render as raw JSON on the storefront no matter how it is bound, which removes that entire failure class.

## **Execution Workflow**

**RUN MODE, read this before doing anything else in this document.**

This document runs in one of two modes, set by Q9 (Manual / Scheduled). Determine the mode first, before any other step, and obey it everywhere below, not just in Phase 0\.

**Manual**, a human is present and watching. Behave as written: confirm the store and wait for the user to confirm it's correct; if any brief question is missing, ask for it and wait; run the style reference and test flow in Phase 0 and wait; and wherever a later phase says to ask the user something or offer a retry or re-run, do so and wait for their reply.

**Scheduled**, no human is present. Never wait for a reply at any point in this entire document. Specifically:

* Do not confirm the store. State which store is being edited in one line and proceed.

* Do not ask about missing or unclear brief questions. If the brief is incomplete or malformed, do not wait: stop and output a one-line error saying which question is missing, then end. A scheduled run must never sit waiting for input.

* If Q2 is "Test With One", or Q2 is "Other" with no number given, that is a malformed brief: one-line error, then end.

* If the universal-with-metafields template does not already exist on the draft theme, stop with a one-line error telling the user to run this document manually once first. Template creation is manual-only.

* Skip the style reference widget entirely; use each product's own images as the only generation reference.

* At every Summary and Verification step, do the reporting as written but never ask "do you want to retry?" or "should I re-run?"; just report what happened and finish.

* The only things that may halt a scheduled run are a genuine tool error or a zero-match scope. Both halt and report (print what happened and stop); neither waits for input.

When this block conflicts with any later instruction in the document (for example a phase that says "ask the user"), this block wins.

### **Phase 1: Template (Silent)**

**Idempotency check first.** If templates/product.universal-with-metafields.json already exists on the draft theme, skip all template creation, ignore Q3, verify the existing bindings (Phase 3 check), and continue to Phase 2\. This makes every re-run and every scheduled run safe.

**Otherwise create it, per Q3. The template is always named "universal-with-metafields" and always built on the draft theme.**

**NESTING RULE (applies before adding any block on every path):** First read the theme's DEFAULT product template JSON and locate its existing Product title and Price blocks. Note their exact nesting level. Some themes place product blocks directly in the section root; others nest them inside a container or group block (often named Details, Group, or similar). Insert every block at the SAME nesting level as the theme's own title and price blocks, inside the same parent, preserving the listed order. Never add content blocks as siblings of a container that holds title and price. After building, verify: if any block sits outside the parent that contains Product title, move it inside before proceeding.

**Section rules (every path):** use only the theme's built-in sections and presets as they appear in the editor's Add Section list; never create custom liquid sections, with ONE exception: the Benefits checklist product block in Appendix A, installed exactly as specified there. Before inserting the benefits block on any path, check whether the theme's product section schema already contains a block of type "benefits"; if it does not, install it per Appendix A first (snippet file, renderer branch, schema entry). The install is idempotent: if the block type already exists, change nothing and just place the block. Remove anything email-related and any pop-ups encountered. All buttons: black background, white text, no hover animation. Any section that asks for a background color: pure white. In the three image-with-text sections, the ONLY allowed blocks are the image, one header, and one body: delete every other preset block (captions, buttons, spacers) before binding.

**Path A, build from scratch (Q3 \= basic one from scratch).** Inside the Product block, in this order:

* Product Title

* Product Price

* Benefits checklist block (the Appendix A custom block), directly below Product Price. Its text\_1 to text\_3 settings carry the benefit1..3 bindings; text\_4 to text\_6 stay blank so they hide.

* Buy Buttons

* Collapsible row "Description" containing the product description dynamic source

* Collapsible row "Shipping and Returns" as a placeholder for now

Below the Product block, in this order:

* Icons with Text (4 icons, horizontal, very light grey background): Truck/Box icon "Fast And Free Shipping" / "Fast and free, anywhere in the world"; Person icon "Dedicated Support Team" / "We care about your experience with us"; Return icon "Easy 30 Day Returns" / "Quick and easy returns with no hassle"; Lock icon "Secure Payments" / "Encrypted and safe checkout"

* Image with Text, image left (iwt1)

* Image with Text, image right (iwt2)

* Image with Text, image left (iwt3)

* Icons with Text (3 icons): Leaf/Box icon "Durable Materials" / "Long lasting and durable materials"; Star icon "Timeless Designs" / "Every product is always time tested"; Ruler icon "Easy Setup Everytime" / "Hassle free setup and accurate sizing"

* Collapsible Content (FAQ), heading "Frequently Asked Questions": exactly FIVE rows, all created BLANK and bound to faq1..5. No static rows; every FAQ on the page is per-product.

* Image Banner (or any image-only section), closing

If the theme has no icons-with-text section, use multicolumn with the theme's icon block instead.

**Path B, Store Builder design (Q3 \= inspiration-universal).** Read templates/product.inspiration-universal.json from the draft theme and copy it as the base for universal-with-metafields. Never modify inspiration-universal itself. Then make ONLY these additions and touch nothing else in the copied template:

* A Benefits checklist block (the Appendix A custom block) inserted directly above the Buy Buttons, inside the same parent as Product Title per the Nesting Rule. text\_1 to text\_3 carry the benefit1..3 bindings; text\_4 to text\_6 stay blank.

* Three image-with-text sections placed directly below the main product section (iwt1..3, image left / right / left), moving every existing image section down below them.

* FAQs: if the base template already has a collapsible content section, bind its first three rows to faq1..3 (the Store Builder reserves rows 1 to 3 blank for exactly this) and insert two more rows directly after them bound to faq4 and faq5, before any static rows. If it has no FAQ section, append a new one with five bound rows before the closing banner. After binding, delete every remaining static row from that FAQ section so it contains exactly the five bound rows; on every path, all FAQs on the page are per-product.

If inspiration-universal does not exist on the draft theme: Manual mode, say plainly that the Store Builder design can't be found on this theme and ask whether to build from scratch instead, then wait. Scheduled mode, one-line error, end.

**Path C, own template (Q3 \= my own template).** Read the named template from the draft theme, copy it as the base for universal-with-metafields, never modify the original, and apply exactly the same three additions and FAQ rule as Path B. If the named template does not exist: Manual mode, ask for the correct name and wait. Scheduled mode, one-line error, end.

**Finish (every path):** Upsert the template file in one call to the draft theme. Save the field-to-metafield-key map to bindings.json (Claude built or placed every section, so every block ID is already known). Do NOT assign the template to any product yet; assignment happens in Phase 6 so no product ever shows an empty page. Output to user: Template ready.

### **Phase 2: Ensure Metafield Definitions (Silent, Idempotent)**

Definitions must exist before any binding validates, so this runs before autobinding. Query existing custom product metafield definitions. Create only the missing ones from the convention list. Types: single\_line\_text\_field for benefits, iwt headings, and FAQ questions; multi\_line\_text\_field for iwt bodies and FAQ answers; file\_reference (image) for iwt images. Never rich\_text\_field. Batch all creates into one aliased mutation. Skip any that already exist.

### **Phase 3: Autobind Template Fields (Silent)**

For each mapped field, write its dynamic source into the template JSON. Binding syntax for EVERY field (text and file image):

{{ product.metafields.custom.\<key\>.value }}

With plain text metafields there is no rich text binding syntax to get wrong. Write all edits into the template JSON in one pass, then upsert the template file in a single call to the draft theme. Do not touch any other section or setting; only the mapped fields change (the block cleanup already happened in Phase 1). After the upsert, re-read the template and confirm every mapped field now carries its dynamic source. If a specific field did not take the binding, list only that field by name and its section, then continue with the rest. Never refuse the whole run for one field.

### **Phase 4: Generate Copy (Silent, Offline)**

Resolve the product scope from Q1 (products(query:) for a name, tag, or collection; paginate past 50 with the after cursor), apply the Q2 count and the already-filled skip rule from Phase 0 Step 4, and save the final list to products.json. For each product, from its title, type, and existing description, write:

* 3 benefits, checkmark headings. Each 8 words or fewer, concrete and real (for example "Adapts through every trimester", "Squat proof and fully opaque"). No filler.

* 3 image-with-text pairs, a short punchy header plus a 1 to 2 sentence description each, on brand per Q5 and using the Q6 store name where natural.

* 5 FAQ Q\&A, every single one about the product itself: what it does, fit and sizing, materials, setup, use, care. Every FAQ is framed positively; a question may voice a buyer's curiosity, but every answer reassures and sells. NEVER write shipping, returns, delivery, refund, or policy FAQs; shipping already lives in its own dropdown. These must not duplicate any static FAQ rows already in the template.

Build all copy for all products in one offline pass. Do not show drafts unless asked.

### **Phase 5: Generate Images in Parallel Batches**

Submit one Higgsfield image job per image-with-text header (3 per product), derived from that header plus the product reference.

* **Model: ALWAYS the latest nano banana (nano\_banana\_pro).** This value is final and overrides any tool recommendation. The server may report the served model under an alias; that is not a failure.

* Pick each product's best existing image (largest, clearest) as the identity reference and save the reference URL per product. Import it with media\_import\_url to get a media\_id; the medias value is always a media\_id, never a raw URL.

* Put model, prompt, aspect\_ratio, and medias all inside the params object. aspect\_ratio: "3:4". medias: the product reference first as \[{ role: "image", value: "\<media\_id\>" }\], then any Phase 0 style reference media IDs after it.

* Prompt (Q4 \= Lifestyle): "Place the product in a natural, real-world lifestyle setting where it would actually be used. If it is worn or carried, show it worn by an appropriate person, child, baby, or pet in a candid editorial style. If it is used in a space, show it on the right surface or environment with subtle context props or hands in frame if appropriate. The product is clearly recognizable and in sharp focus, but the scene feels lived in and authentic rather than staged. No text at all. Use the first reference image to identify the product, then place it convincingly in the moment of use. Match the mood, lighting, and composition of the other reference images. Match the mood of the image-with-text header: \<header\>."

* Prompt (Q4 \= Pure white): "Pure white seamless studio background (\#FFFFFF), soft even product photography lighting, only a subtle natural ground shadow. The product occupies roughly 60 to 70% of the frame, centered, crisp and sharp. No props, no people, no background elements, no text. The product is unmistakably the single hero."

* Prompt (Q4 \= Your design): build the prompt from the user's description, always ending with: "The product from the first reference image is clearly recognizable and in sharp focus. No text at all."

* Submit as many as possible at once, ideally via generate\_image\_batch plus jobs\_wait. On the concurrent-jobs cap, wait 10 to 15s and retry; jobs drain as they finish. Save the job-ID to (product, slot) map to jobs.txt continuously as you submit; this is the only recovery path if the run dies. Poll to completion before importing.

**Output** after each batch: Products X to Y images submitted. Then Waiting for image rendering... and poll until each completes.

**Error handling, three distinct types:**

* **Concurrent-jobs / rate limit** (explicit "too many jobs"): wait 15s, retry the same job unchanged. Always recoverable; never counts toward the stop rule. If still failing after 2 tries, wait again; if no image after that, stop.

* **Hard limit** (credits exhausted, account cap): stop submitting, attach whatever rendered, set every text metafield, and report. Products missing any image are NOT finished: they keep their Q7 tag and their current status so the next run picks them up.

* **Generic job failure** ("Something went wrong" or a job that errors out): NOT automatically a rate limit. Wait 20s, retry once on the same reference; if it fails again, retry once on the product's 2nd reference image; only if that also fails is the product counted as failed. Log its ID to failed\_images.txt and move on. Do not keep hammering the original reference.

**Stop rule.** Count only distinct products that failed after the full escalation above. Raw retries on a single product never count. If 3 distinct products fail in a row, stop and tell the user what to do. A single bad reference must never trip the stop rule.

### **Phase 6: Import Images, Set All Metafields, Assign Template (Silent)**

Higgsfield result URLs are public CloudFront links; Shopify ingests them directly via originalSource. No staged upload needed.

* Import images: fileCreate with originalSource: \<cloudfront\_url\>, contentType: IMAGE, a descriptive alt. Batch all images in one call. Capture each new MediaImage GID.

* Set metafields for each product in one metafieldsSet call per product (25 or fewer each): benefit1..3, iwt1..3\_heading, faq1..5\_q as the generated strings; iwt1..3\_body and faq1..5\_a as plain strings with line breaks as \\n; iwt1..3\_image as file\_reference with the imported MediaImage GID.

* Assign the universal-with-metafields template to each product whose metafields are now fully set. Because the template fields are bound to these metafields, the page is complete the moment assignment lands. Never assign the template to a product whose fields are not set.

### **Phase 7: Finish Products (Q7 and Q8, Silent)**

A product counts as completed only when all its text metafields, all three images, and the template assignment landed. For each completed product, in one productUpdate per batch of 10:

* If Q7 is Yes: remove exactly the named tag from the product's tag list, touch no other tag, and push the full remaining list.

* If Q8 is Yes: set status to ACTIVE.

Products that did not complete (failed or missing images) keep their tag and their current status so a later run picks them up automatically.

### **Phase 8: Verification Check**

Don't assume, confirm the work landed:

* Re-read the template and confirm every mapped field still carries its dynamic source binding, every block sits at the correct nesting level inside the Product parent, and the image-with-text sections contain only image, header, and body blocks.

* Query each product's metafields back and confirm the benefits, headings, and questions resolve to the new copy, and each iwt image reference resolves to a MediaImage { image { url } } with an hf filename.

* Confirm completed products carry the template, lost the Q7 tag, and hold the Q8 status; confirm incomplete products kept their tag and status.

* Spot-check the storefront preview of a sample product (/products/\<handle\>?view=universal-with-metafields\&preview\_theme\_id=\<draft id\>) and confirm the benefits checklist renders below the price with its checkmarks, the image-with-text sections show their images and copy, and all five FAQ rows show the metafield content as visible text. Open this link with Claude in Chrome ONLY on the run that first built the template; on every other run, verify through the read-backs above and do not use Chrome.

* Report any product where a slot is still blank or old, or any field where the binding did not take. Manual: offer to re-run just those. Scheduled: report and finish, never offer.

"Mutation succeeded with no userErrors" does NOT guarantee the visible result is correct.

### **Phase 9: Summary**

Report the template created or reused, how many products were filled, how many fields bound, how many images generated and attached, how many products were tagged out and set active, and any failures with the reason. Manual: ask whether to retry failures. Scheduled: report and finish, never ask. Remind the user the template lives on the DRAFT theme and shows on the storefront once that theme is published. ALWAYS end the summary (and the test result in Phase 0\) with a link to view a built product page: /products/\<handle\>?view=universal-with-metafields\&preview\_theme\_id=\<draft id\>, using a product completed in this run. Every run's final message ends with that link. Then LASTLY\*\*\*\* remind the user that the product page template is built, and check if the products they selected were added to it. If not, instruct them how to do it manually, and ask them if they want you to add products to this template instead.  

## **Context Efficiency Rules**

CRITICAL, follow to prevent context bloat:

* Never echo GraphQL schema dumps to the user. Use graphql\_schema internally only.

* Minimize response fields. Request only userErrors in mutations. Extract data with jq/Python before displaying.

* Batch aggressively: one upsert for the template build; one aliased mutation for all definition creates; one upsert for all bindings; one fileCreate for all images; one metafieldsSet per product; 10 products per productUpdate call. Submit image jobs as fast as the concurrent limit allows.

* Build all batch payloads offline in one pass, then fire mutations with zero round-trips between them.

* Parse large JSON offline (save to files, process with Python/jq). Show only summary lines.

* Keep progress reports under 50 characters.

## **Hard-Won Notes (read once)**

* All dynamic sources end in .value. Because every copy field is plain text, there is no metafield\_tag or rich text syntax anywhere in this build.

* A dynamic source only validates if its metafield definition already exists, so create definitions (Phase 2\) before autobinding (Phase 3).

* Read the default product template first and match its nesting; themes differ on whether title and price live in the section root or inside a group block.

* Higgsfield caps concurrent jobs; expect rate-limit responses and drain-and-retry.

* If one field ever rejects its binding, name that single field and continue; never make the student bind anything.

## **Recovery from Failures**

* Context limit mid-run: save state (last completed product and phase) to checkpoint.json. User resumes with "Continue from product N".

* Credits exhausted: flag the image phase incomplete in the summary; text metafields are still set, but affected products keep their tag and status and are NOT assigned the template until their images land on a later run.

* Binding rejected on a specific field: name that field and its section in the summary, keep every other binding and value, and offer to re-run just that field (Manual only).

* Template creation fails on a specific section (preset missing in this theme): substitute the closest built-in section of the same type, note the substitution in the summary, and continue.

**A.5 Replicating on any theme.**

* Find the file that renders the product blocks. In Impulse it is snippets/product-template.liquid. In Dawn style themes each block is its own file under blocks/ or a case in sections/main-product.liquid.

* Add one when branch for the 'benefits' block type that renders the snippet.

* Add the matching entry to the blocks array of the product section's {% schema %}. The type string in the schema must match the when string exactly.

* Keep the markup in the snippet, not inline in the case, so the same code stays identical across themes.

* The CSS is scoped with {{ block.id }} so two copies on one page never fight each other.

* A repeating list inside a single block cannot use child blocks, so the numbered text settings (text\_1 to text\_6) are joined with a separator and split in Liquid. Blank lines are skipped, which is why text\_4 to text\_6 stay empty.

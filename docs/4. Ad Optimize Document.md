Error handling — two distinct error types:

* **Concurrent-jobs error** (explicit "too many jobs" / rate-limit message) → wait 15s and retry the same job. Always recoverable; never counts toward the stop rule. If it doesn’t work again, wait another 15s. If more than 2 tries with this with no updated image, stop.   
* **Hard limit** (credits exhausted, account cap) → stop submitting, attach whatever rendered and set as featured, report.  
* **Generic job failure** (a non-specific error such as "Something went wrong", or a job that errors out) → this is NOT automatically a rate-limit. Handle it as a per-product failure with a defined escalation:  
* Wait 20s, then retry **once** on the same reference image.  
* If it fails again, retry **once** on the product's 2nd reference image URL.  
* Only if the 2nd reference also fails is the product counted as **failed**. Log its product ID to `/home/claude/work/failed_images.txt` and move on to the next product.  
* Do not keep hammering the original reference. 

**The stop rule.** Count only **distinct products that failed after the full escalation above** (i.e. after the 2nd-reference fallback also failed). Raw retry attempts on a single product never count. If **3 distinct products** fail in a row this way, stop operations and tell the user what to do. A single bad reference file must never trip the stop rule.

Do NOT stop the batch for individual failures. A job may sit `in_progress` longer than expected — re-poll, don't assume done. But if 3 separate products fail in a row, stop operations and tell the user what to do.

Output after submitting each batch of 10: `"Products X–Y images submitted"`

Check job status via `higgsfield:job_display` after all jobs are submitted. Output: `"Waiting for image rendering..."`

### **Phase 3: Attach Finished Images and Set as Featured (Silent)**

Higgsfield result URLs are public CloudFront links — Shopify ingests them directly via `originalSource`. No staged upload needed.

**Step 1 — Attach.** `productCreateMedia` is deprecated; use `productUpdate` with the `media` arg:

mutation($pid0: ID\!, $m0: \[CreateMediaInput\!\]\!, ...) {

  c0: productUpdate(product: {id: $pid0}, media: $m0) { userErrors { field message } }

}

`CreateMediaInput` fields: `originalSource` (the URL), `mediaContentType: IMAGE`, `alt`. Batch \~10 per call.

**Step 2 — Set as featured (required).** Attaching adds the image to the end of the media list — it does NOT become the featured image. Query each product's media list, find the new image by matching the Higgsfield filename (`hf_...`), get its `MediaImage` ID, then call `productReorderMedia(id: <productId>, moves: [{id: <mediaImageId>, newPosition: "0"}])`. Notes: `newPosition` is zero-based (`"0"` \= featured) and must be sent as a string, not a number. Batch \~10 reorders per call. Verify with a `featuredMedia` query on a sample.

## **Context Efficiency Rules**

CRITICAL — Follow to prevent context bloat:

* Never include schema dumps in visible output. Use `Shopify:graphql_schema` internally; don't echo to user.  
* Minimize GraphQL response fields. Request only `userErrors` in mutations. Extract data with jq/Python before displaying.  
* Batch aggressively. 10 products per GraphQL call (mutation aliases). Submit image jobs as fast as the concurrent limit allows.  
* Build all batch payloads offline in one pass, then fire mutations with zero bash round-trips between them.  
* Parse large JSON offline. Save responses to files, process with Python/jq. Show only summary lines.  
* Keep progress reports under 50 characters. ✓ `"Products 10–19 images submitted"`

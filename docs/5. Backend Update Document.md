# **Backend Update Document**

## **The Brief**

* **Q1** — What products to update: (All / Draft status only / Active status only / By Tag)  
* **Q2** — Pricing adjustment: (Keep current / Increase 20% / Decrease 5% / Double)  
* **Q3** — Minimum Price (None / $19.99 / $29.99 / $39.99 / $49.99)  
* **Q4** — Price rounding: (Nearest $.99 / Nearest $EvenNumber.99 / Nearest $4.99 or $9.99 / No rounding)  
* **Q5** — What status to set: (Active / Draft / Keep current status)  
* **Q6** — Title rewriting: (Rewrite titles / Keep current titles)  
* **Q7** — Description rewriting: (Rewrite descriptions / Keep current descriptions)  
* **Q8** — Seasonal tagging: (Auto-infer per product / Tag all as \[season\] / Skip seasonal tagging)  
* **Q9** — Title / SEO title format: (Use default format / I'll specify my own: \[Your format\])  
* **Q10** — Should we confirm steps with you? (Yes this is a manual task / No this is a scheduled task)

## **Purpose**

Batch update Shopify products: rewrite titles, descriptions, SEO title, SEO description, adjust pricing, set status, apply seasonal tags. Execute efficiently with minimal context bloat.

## **Content Formats**

When a field is being rewritten, it must follow these formats exactly. All character limits are **hard limits** — the Python script must trim or regenerate any field that overflows so every field fits before it is pushed.

### **Titles (whether to rewrite is controlled by Q6; the format is controlled by Q9)**

Q6 governs WHETHER the product title and SEO title are rewritten — they are rewritten together. 

Q9 governs the FORMAT they are rewritten into: 

**Use default format:** 

* **Product title** (`title`): a short product name, **under 60 characters**.   
  * Example: `WaterBead Jacket`  
* **SEO title** (`seo.title`): format `[Product Name] - [keyword-rich descriptor]`, **under 70 characters**. The descriptor is a comma-separated run of keywords describing the product.  
  * Example: `WaterBead Jacket - Comfy, Water Resistant, Oversized Rain Jacket`

**I'll specify my own:** 

* Use exactly the title/SEO format the user pasted in their brief instead of the default above. Still enforce the hard character limits (title under 60, SEO title under 70\) — if the user's format would overflow, trim to fit. If the user selected "I'll specify" but pasted no format, treat it as a missing brief answer (Manual: ask for it; Scheduled: error out per the RUN MODE block).

**Descriptions (controlled by Q7)**

Q7 governs BOTH the product description and the SEO description — they are rewritten together.

* **Product description** (`descriptionHtml`): exactly 3 paragraphs minimum of 200 words, maximum 250, followed by a bulleted spec list at the end. Render as `<p>` paragraphs and a `<ul>` of `<li>` spec items.  
* **SEO description** (`seo.description`): a single sentence, keyword-dense (pack in as many relevant keywords as read naturally), **under 160 characters**.

### **Brand source**

Where a rewrite needs the brand name, pull it from the Shopify’s store name you are currently working on. If there is no store name (“My Store” or similar), then prompt the user for their store name.

**Seasonal tags (controlled by Q8)**

Q8 controls a single seasonal tag drawn from this fixed vocabulary: `winter`, `spring`, `summer`, `fall`, `evergreen`.

* **Auto-infer per product**: read each product's title, type, and description and pick the best-fit season. Use `evergreen` as the fallback when nothing seasonal is obvious (e.g. a phone case, a year-round household item).  
* **Tag all as \[season\]**: apply the one season named in the brief to every product.  
* **Skip seasonal tagging**: do not touch tags at all.

Tag handling rules:

* The seasonal tag is **added** to the product's existing tag list. Non-seasonal tags are never removed or altered.  
* Do not strip a previously-applied season tag. (Note: across re-runs this means a product can accumulate more than one season tag.)  
* Never add the same tag twice — dedupe against exact repeats so a product cannot end up with `summer` listed twice.  
* Build the final tag list as `existing_tags ∪ {season}` and push it via `ProductUpdateInput.tags`.

## **Execution Workflow**

**RUN MODE — read this before doing anything else in this document.**

This document runs in one of two modes, set by the run-mode question in the brief (Manual / Scheduled). Determine the mode first, before any other step, and obey it everywhere below — not just in Phase 0\.

**Manual** — a human is present and watching. Behave as written: confirm the store and wait for the user to confirm it's correct; if any brief question is missing, ask for it and wait; ask the test-run question (below) and wait; and wherever a later phase says to ask the user something or offer a retry/re-run, do so and wait for their reply.

**Test-run question (Manual only):** After confirming the store and brief, ask the user — "Would you like to do a test run on one product first, or run the full batch?" Then STOP and return control to the user. Change nothing until their next message answers. If they choose test: process exactly one in-scope product fully \[for images: generate, attach, set as featured / for backend: text, price, status, tags / for sale: apply the compare-at sale\], show them the result, then stop again and wait for approval before running the rest. If they would like to change anything, they may tell you here. When you run the rest, skip the product you already did.

**Scheduled** — no human is present. Never wait for a reply at any point in this entire document. Specifically:

* Do not confirm the store. State which store is being edited in one line and proceed.  
* Do not ask about missing or unclear brief questions. If the brief is incomplete or malformed, do not wait — stop and output a one-line error saying which question is missing, then end. A scheduled run must never sit waiting for input.  
* Skip the test-run question entirely.  
* At every Summary and Verification step, do the reporting as written but never ask "do you want to retry?" or "should I re-run?" — just report what happened and finish.  
* The only things that may halt a scheduled run are a genuine tool error or a zero-match scope. Both halt-and-report (print what happened and stop); neither waits for input.

When this block conflicts with any later instruction in the document (e.g. a phase that says "ask the user…"), this block wins.

### **Phase 1: Fetch and Prepare (Silent)**

Fetch all in-scope products via `Shopify:graphql_query`:

query($query: String\!, $first: Int\!, $after: String) {

  products(query: $query, first: $first, after: $after) {

    edges {

      node {

        id

        title

        descriptionHtml

        vendor

        productType

        tags

        status

        seo { title description }

        variants(first: 100\) {

          edges { node { id price title } }

        }

      }

    }

    pageInfo { hasNextPage endCursor }

  }

}

Paginate if \>50 products (use `after` cursor). Save to `/home/claude/work/products.json`.

Generate all rewrites offline in a Python script. For each product:

* Rewrite description \+ SEO description per the Content Formats above, but only if Q7 \= "Rewrite descriptions". If Q7 \= "Keep current descriptions", do not include `descriptionHtml` or `seo.description` in the payload.  
* Rewrite title \+ SEO title per the Content Formats above, but only if Q6 \= "Rewrite titles". If Q6 \= "Keep current titles", do not include `title` or `seo.title` in the payload.  
* Calculate new price per Q2, then round per Q4 with a minimum of Q3.  
* Determine the seasonal tag per Q8 (skip entirely if Q8 \= "Skip seasonal tagging"), then build the final tag list as the product's existing tags plus the season tag, deduped.  
* Enforce all character limits: any title ≥60, SEO title ≥70, or SEO description ≥160 chars must be trimmed or regenerated to fit before being saved.

Save to `/home/claude/work/rewrites.json`:

    "title": "WaterBead Jacket",

    "descriptionHtml": "\<p\>Para 1...\</p\>\<p\>Para 2...\</p\>\<p\>Para 3...\</p\>\<ul\>\<li\>Spec...\</li\>\</ul\>",

      "title": "WaterBead Jacket \- Comfy, Water Resistant, Oversized Rain Jacket",

Include `title` \+ `seo.title` only if Q6 \= "Rewrite titles". Include `descriptionHtml` \+ `seo.description` only if Q7 \= "Rewrite descriptions". Include `status` only if Q5 ≠ "Keep current status". If Q6 rewrites titles but Q7 keeps descriptions (or vice versa), the `seo` object carries only the half being rewritten.

Output to user: `"Backend preparation complete (N products)"`

### **Phase 2: Push Text \+ Price \+ Status in Batches of 10**

Build all batch payloads offline in one Python pass first, writing each batch to its own JSON file. Then fire the mutations with zero bash round-trips between them — this is the single biggest speed-up; data streaming through chat is what makes runs slow.

Execute batched GraphQL mutations, 10 products per call. `productUpdate` takes `ProductUpdateInput!` and the argument is `product:` (NOT `input:` / `ProductInput!`):

mutation($ip0: ProductUpdateInput\!, $pid0: ID\!, $vr0: \[ProductVariantsBulkInput\!\]\!,

         $ip1: ProductUpdateInput\!, $pid1: ID\!, $vr1: \[ProductVariantsBulkInput\!\]\!, ...) {

  p0: productUpdate(product: $ip0) { userErrors { field message } }

  v0: productVariantsBulkUpdate(productId: $pid0, variants: $vr0) { userErrors { field message } }

  p1: productUpdate(product: $ip1) { userErrors { field message } }

  v1: productVariantsBulkUpdate(productId: $pid1, variants: $vr1) { userErrors { field message } }

  ...

}

* Use mutation aliases (`p0:`, `v0:`, ...) to batch 10 products per call.  
* `ProductUpdateInput` carries `id` plus the fields being changed: `descriptionHtml` and `seo.description` if Q7 \= "Rewrite descriptions"; `title` and `seo.title` if Q6 \= "Rewrite titles"; `status` if Q5 ≠ "Keep current status"; `tags` (the full deduped list) if Q8 ≠ "Skip seasonal tagging". SEO fields go in a nested `seo: { title, description }` object on `ProductUpdateInput`.  
* Variant prices go through `productVariantsBulkUpdate` — `productId` \+ a `variants` array of `{id, price}`. Skip the `v` alias entirely if Q2 \= "Keep current prices".  
* Request only `userErrors` in the response.  
* Check `userErrors` for failures, log them, continue.  
* Output after each batch: `"Products X–Y backend done"`

## **Context Efficiency Rules**

CRITICAL — Follow to prevent context bloat:

* Never include schema dumps in visible output. Use `Shopify:graphql_schema` internally; don't echo to user.  
* Minimize GraphQL response fields. Request only `userErrors` in mutations. Extract data with jq/Python before displaying.  
* Batch aggressively. 10 products per GraphQL call (mutation aliases).  
* Build all batch payloads offline in one pass, then fire mutations with zero bash round-trips between them.  
* Parse large JSON offline. Save responses to files, process with Python/jq. Show only summary lines.  
* Keep progress reports under 50 characters. ✓ `"Products 10–19 backend done"`
